# Run R3: first real video into the camera

R3 is split in two halves that meet at the wire protocol:
- **Windows half (done, 2026-11-21):** engine receives H.264 → decodes → feeds Cabled Camera. Proven with the fake phone.
- **iPhone half (next):** companion captures the camera and hardware-encodes H.264 into the same VIDEO messages. Written from the Windows PC and built by CI. The owner installs it with SideStore (D-15: the Mac can't run a current Xcode). Needs R1's device results first.

## Windows half: what was built

| Piece | Where |
|-------|-------|
| Protocol additions: CONFIGURE / CONFIGURED / VIDEO / KEYFRAME_REQUEST (version stays 0.1, pure additions) | `windows/src/common/protocol.*`, `docs/transport-and-protocol.md` |
| VIDEO payload codec + H.264 helpers (Annex-B/AVCC, access-unit splitting, IDR detection) | `windows/src/common/video.*` |
| Fake phone streams an H.264 clip after CONFIGURE, at the configured fps, jumps to the next IDR on KEYFRAME_REQUEST, can simulate lost frames | `windows/src/common/fake_phone.*`, `cabled-fakephone --clip` |
| Stamped test clip: our test pattern (frame number in the pixels), H.264 High, no B-frames, keyframe every 1 s, SPS/PPS on every keyframe, BT.709 | `windows/testdata/pattern_1080p30.h264` (21 KB, 120 frames) |
| Engine: FFmpeg H.264 decoder (D3D11VA hardware, software fallback), converter (plain copy when formats match, swscale otherwise), virtual camera output (publishes in the format the app chose), session (handshake, ping clock sync, CONFIGURE, gap → keyframe request) | `windows/src/engine/` |
| `cabled-engine`: the headless engine, over USB or `--tcp` to the fake phone | `windows/tools/engine/main.cpp` |
| FFmpeg 9.0.2 via vcpkg (manifest, pinned baseline 2026.10.16): avcodec + swscale, LGPL, shared DLLs | `windows/vcpkg.json` |
| `cabled-vcam check` now also reports **sample age**: capture → app latency for any source | `windows/tools/vcam/main.cpp` |
| Tests: 4 video-format tests, 4 engine tests (software decode in order, hardware decode, lost-frame recovery, refused CONFIGURE). **33/33 pass locally** | `windows/tests/` |

## Results (dev PC: RX 9070 XT, fake phone on the same machine)

Fake phone → H.264 over TCP → engine → frame ring → Frame Server → app (`cabled-vcam check`):

| App asked for | Engine path | FPS | Capture → app, median / p95 |
|---------------|-------------|-----|-----------------------------|
| NV12 1080p30 (default) | D3D11VA decode → plain copy | 30.0 | **2.8 / 4.0 ms** |
| NV12 720p30 | decode → swscale resize | 30.0 | 3.9 / 5.4 ms |
| RGB32 720p30 | decode → swscale convert | 30.1 | 7.3 / 8.5 ms |

- **Hardware decode** (D3D11VA on the RX 9070 XT) takes about 2.3 ms per 1080p frame, including the copy back to system memory.
- **No frames skipped**, no sequence gaps, and the stamped frame numbers decode in order.
- When the app changed formats, the engine followed within a frame. When no app had the camera open, the engine went idle and published nothing.
- **Lost frames recover cleanly:** gap → KEYFRAME_REQUEST → frames dropped until the next IDR → resume, with zero decode errors and no corrupted pictures (test `Engine.RecoversFromLostFramesWithKeyframeRequest`).

**Caveat:** the clip is synthetic (21 KB for 4 s), so these numbers say nothing about bitrate or USB throughput. Those come from the real iPhone (R1 probe numbers, then R3's iPhone half).

## Try it yourself (no iPhone needed)
Three terminals, then pick "Cabled Camera" in OBS or a browser:

```powershell
.\build\bin\Release\cabled-fakephone.exe --clip windows\testdata\pattern_1080p30.h264
```
```powershell
.\build\bin\Release\cabled-engine.exe --tcp 127.0.0.1:47800
```

You should see the colour bars with the moving box, now going through a real H.264 encode and decode.

## Decisions and notes
- **D-05 detail:** FFmpeg comes from vcpkg's `x64-windows` triplet (DLLs with the dynamic VC++ runtime). Our own code stays on the static CRT. Nothing CRT-owned crosses the FFmpeg boundary, so mixing is safe. The installer (R11) must ship the VC++ runtime DLLs or the redistributable alongside the FFmpeg DLLs.
- First configure builds FFmpeg from source (~10 minutes on the dev PC). CI caches the vcpkg binary packages.
- The engine is still single-threaded (receive → decode → publish on one thread). R4 splits it with latest-frame mailboxes (architecture.md) and adds reconnect and a minimal UI.

## iPhone half: what it has to do (CI-built, no Xcode debugging)
1. Add CONFIGURE/CONFIGURED/VIDEO/KEYFRAME_REQUEST to `WireProtocol.swift`, same IDs and layouts (test vectors from `windows/tests/video_tests.cpp`).
2. `CameraController`: rear main camera (D-26), 1080p30, `420v`, stabilisation off, rotation via `videoRotationAngle`.
3. `Encoder`: VTCompressionSession H.264 High, real time, no frame reordering, bitrate from CONFIGURE, keyframe every 2 s and on KEYFRAME_REQUEST, output AVCC with SPS/PPS prepended on keyframes.
4. Send queue capped at 2 frames: on stall, drop until the next keyframe (transport-and-protocol.md, flow control).
5. Device test: `cabled-engine` over USB → Cabled Camera in OBS/Teams. Measure glass-to-glass with a phone filming a ms clock.
