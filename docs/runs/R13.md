# R13: soak, thermal, latency, recovery

## What was built

- **GPU reset recovery (TDR):** a GPU reset leaves FFmpeg's D3D11VA decoder dead; this also covers a driver update, or sleep on some laptops. Before, every packet failed, keyframes included, and the engine asked for keyframes forever.
  - Now, after 8 failed packets in a row, the decoder is rebuilt on a fresh D3D11 device.
  - If the rebuilt hardware decoder fails again in the same session, the engine switches to software decoding until the next connection.
  - Diagnostics counts "decoder rebuilds".
- **Thermal hysteresis** (`ThermalGovernor`, unit-tested):
  - Hotter phone states apply at once.
  - Cooler states apply only after the phone has stayed cooler for 60 s. Before, a phone hovering between "fair" and "serious" switched the capture back and forth, a glitch each time.
  - The status line now says "Your iPhone is hot: reduced to 1080p30 until it cools down" (720p30 when critical), as planned in windows-app.md.
- **Image adjustments made cheaper** (from the R14 bug bash):
  - Sharpening is now a separable box blur.
  - Brightness and contrast are folded into the same pass.
  - All adjustments at once cost 3.5 ms per 1080p frame and 14.5 ms per 4K frame (was 5.6 and 23.8). A 4K60 output now fits within one frame.
- **Soak tool:** `windows\scripts\soak.ps1 -Minutes N [-Camera]`. It runs the fake phone and the headless engine for N minutes and samples memory, handles, threads and CPU every 30 s. The results go to `build\soak-*.csv`, with the engine's own per-second stats in `build\soak-*-engine.log`.

## Checked by reading the code (not changed)

- **Frame Server restart:**
  - The camera DLL (inside Frame Server) creates the shared frame ring, and the engine opens it.
  - When Frame Server restarts, the engine still holds the ring, so the new DLL instance opens the same one.
  - When no app uses the camera, the engine retries opening the ring every second.
- **Sleep, resume, unplug:** the USB session drops, and the engine's reconnect loop and silence watchdog bring it back. The app shows "Connect your iPhone" in the meantime.
- **Latency:**
  - The phone already uses real-time encoding with no frame reordering, plus low-latency rate control where iOS has it. The decoder runs with low-delay flags and no frame threading.
  - Capture-to-decoded latency is measured live in Diagnostics.
  - No further tuning was done in this run. The next step would be the zero-copy GPU path, after 1.0.
  - Owner check 3 below records a real number.

## Soak result (fake phone, this PC)

20 minutes of 1080p30 H.264 from `cabled-fakephone`, decoded on the GPU by `cabled-engine --no-vcam` (2026-11-22, `build\soak-20261122-031228.csv`):

| Measure | Result |
|---|---|
| Frame rate | 30.0 fps average, lowest second 29.2 |
| Keyframe requests (drops) | 0 |
| Reconnects | 0 |
| Private memory, 5 min → 20 min | 87.2 MB → 87.2 MB (no growth) |
| Handles | 837 → 837 |
| CPU | 28.8 s over 1200 s, about 2.4% of one core |

The first run had decoded nothing: `--no-vcam` was broken (see R14). The soak script now prints a warning if nothing streamed.

## Owner checks

1. **Thermal:**
   - Run a 4K call or OBS recording for 20–30 minutes with the phone in a case, in a warm spot.
   - When it gets hot, the status line shows the reduced mode. The picture changes once, not back and forth.
   - About a minute after it cools, quality comes back.
2. **Sleep:** with OBS showing Cabled Camera, put the PC to sleep and wake it up. The video should come back without restarting anything.
3. **Long call:** keep a call running for an hour. Afterwards, Diagnostics should show steady fps and no climbing reconnect count.
