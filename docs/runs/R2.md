# Run R2: Windows 11 virtual camera spike

**Goal** (roadmap.md): a test-pattern "Cabled Camera" registered on the dev PC that real apps can open, plus a working path for frames from a user process (the future engine) into Frame Server. Decides D-09 and whether Windows 11 also needs the DirectShow filter.

**Verdict: the spike succeeded, and the plan holds.** The hardest technical risk in the project (rated 5/5) is retired. No broker service is needed and no DirectShow filter is needed on Windows 11.

## What was built

| Piece | Where |
|-------|-------|
| Media Foundation media source DLL (IMFActivate → IMFMediaSourceEx + IMFMediaStream2, IKsControl stub, provided-allocator support), static CRT, no WRL/WinRT dependency | `windows/vcam/` → `cabled_vcam_mf.dll` |
| Shared-memory frame ring + event (engine ↔ Frame Server), test pattern with machine-readable timestamp and frame-number bands | `windows/src/vcam_shared/` |
| `cabled-vcam` tool: `selftest`, `register`, `remove`, `list`, `feed` (plays the engine), `check` (plays an app, measures fps/latency/content) | `windows/tools/vcam/main.cpp` |
| Browser test page (getUserMedia at 5 sizes, fps, repeats, colour) | `windows/tools/vcam/webcam-test.html` |
| Dev install script (one UAC prompt: copy DLL to Program Files, regsvr32, log folder) | `windows/scripts/vcam-dev-install.ps1` |
| Tests: 4 new unit tests (pattern, padded buffers, ring), `VcamSelftest` (whole source in-process at all 10 formats, pacing checked ±15%) | 25/25 pass locally |

## Results (dev PC: Windows 11 LTSC 26100, RX 9070 XT)

### Through Frame Server, Media Foundation app path (`cabled-vcam feed` + `cabled-vcam check`)
| Format | FPS | Engine → app latency, median / p95 |
|--------|-----|------------------------------------|
| NV12 1080p30 (first in list, the default) | 30.0 | 0.6 / 0.8 ms |
| NV12 1080p60 | 60.0 | 0.5 / 0.8 ms |
| NV12 4K30 | 30.2 | 2.3 / 2.7 ms |
| RGB32 720p30 | 29.9 | 0.6 / 1.5 ms |
No frames skipped. One repeat in RGB32 (expected: the frame-ring cadence). Format switches between apps reconfigure cleanly.

### DirectShow apps (FFmpeg `-f dshow`, the same API OBS and Zoom's DirectShow path use)
- The camera is listed through **Frame Server's DirectShow bridge**. **No DirectShow filter is needed on Windows 11** (D-07).
- Captured 150 frames at 1080p30, exactly 30 fps.
- The bridge also offers **YUY2 versions of every NV12 format** automatically.
- ⚠️ **Colour:** DirectShow carries no colour matrix, so FFmpeg decoded our BT.709 as BT.601. Green 0,191,0 came out as 13,222,4 and red 191,0,0 as 173,0,1. This is the pitfall predicted in video-pipeline.md, now measured. → R12 colour work: check OBS's default colour-space setting, and consider a "compatibility colour" option.

### Chromium (Edge 158; Teams and Discord use the same engine)
| Request | Got | FPS* | Unique frames / repeats | Colours |
|---------|-----|------|-------------------------|---------|
| default (no constraints) | **640×480** | 30 | 91 / 0 | exact (green 0,191,0, red 191,0,1) |
| 720p30 | 1280×720 | 30.1 | 91 / 0 | exact |
| 1080p30 | 1920×1080 | 29.6 | 90 / 0 | exact |
| 1080p60 | 1920×1080 @60 | 55 | 166 / 0 | exact |
| 4K30 | 3840×2160 | 27.3 | 83 / 0 | exact |

\*Measured in JavaScript with a full canvas readback on every frame, so the 1080p60 and 4K numbers are limited by the test page. Every frame it saw was unique.

- Chromium **reads our BT.709 tags through Media Foundation: colours are exact.**
- **With no constraints, Chromium picks 640×480**, because 640×480 is Chromium's own default request. That matters for R5: web apps that don't ask for HD get SD. Options: don't advertise 4:3 SD, or advertise it last. Decide in R5 after checking Meet/Teams-web behaviour.

## Answers to the spike's questions

| Question | Answer |
|----------|--------|
| Does a synthetic MF source work in Frame Server, unsigned? | **Yes.** Unsigned DLL from `C:\Program Files\Cabled\Dev`, loaded into `svchost.exe` (Frame Server) and at creation into FrameServerMonitor |
| Admin needed? | **Only for COM registration** (HKLM, because Frame Server runs as LOCAL SERVICE) and for putting the DLL where LOCAL SERVICE can read it (not a user profile). **`MFCreateVirtualCamera` (System lifetime, CurrentUser access) needs no admin** |
| D-09 IPC | **Decided: no pipe needed.** The media source creates `Global\CabledVCam.v1` (section) and `…Frame` (event) with a DACL for interactive users. Frame Server has SeCreateGlobalPrivilege; the engine opens them by name. The header carries both directions (active format, counters, heartbeats). Bonus: the section exists only while an app has the camera, so the engine can tell when to wake the phone |
| DirectShow filter on Windows 11? | **Not needed.** The Frame Server bridge covers DirectShow apps |
| Device name | Windows appends a suffix: apps show **"Cabled Camera (Windows Virtual Camera)"**. Can't be changed from our side as far as we know |
| Pacing | Wait timeouts round up to the ~15.6 ms system tick (30 fps came out as 21.7). Fixed with a **high-resolution waitable timer** on a fixed cadence: exact 30.0 / 60.0 |
| Gotcha | The stream must be **selected by default** in the presentation descriptor, or plain source readers get `MF_E_INVALIDREQUEST`. Frame Server selects it anyway |

## Not done in R2 (needs you, or later runs)
- **Visual check in OBS, Teams, Zoom, Discord.** Teams, Zoom and Discord need your sign-in, and computer use couldn't take the foreground for OBS while you were working. FFmpeg (DirectShow) and Edge (Chromium/MF) already prove the paths those apps use. Checklist below.
- Windows 10 (DirectShow filter): after 1.0, as agreed.
- Zero-copy GPU texture sharing with Frame Server: not needed yet (4K30 costs 2.3 ms with CPU copies).
- `KSPROPERTY` camera controls through the virtual camera: not planned. Controls live in the Cabled UI.

## Your checklist (10 minutes, optional but useful)
The camera stays installed on this PC, showing the placeholder (dark bars, sliding blue stripe) when nothing feeds it. To show the test pattern, run this in a terminal and leave it open:

```powershell
.\build\bin\Release\cabled-vcam.exe feed
```

Then in each app pick **Cabled Camera (Windows Virtual Camera)** in its video settings and note whether you see colour bars and a moving white box:
- [ ] OBS: Sources → + → Video Capture Device → Cabled Camera
- [ ] Teams: Settings → Devices → Camera
- [ ] Zoom: Settings → Video
- [ ] Discord: User Settings → Voice & Video → Camera
- [ ] Two apps at once (e.g. Teams + OBS): both show the pattern

To remove everything:

```powershell
.\build\bin\Release\cabled-vcam.exe remove
```
```powershell
.\windows\scripts\vcam-dev-install.ps1 -Uninstall
```
