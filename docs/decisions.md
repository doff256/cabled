### D-01 USB transport through Apple Mobile Device Service
- **Context:** USB only, no paid signing, no kernel drivers.
- **Options:** AMDS usbmux · our own usbmux over WinUSB · USB tethering · MFi accessory · kernel driver.
- **Decision:** AMDS. It's the only approach that needs no driver replacement, no hotspot and no certification, and it's how existing iPhone USB webcam apps work.
- **Cost:** users must install Apple Devices or iTunes. That's one extra setup step, handled in onboarding.

### D-02 Our own usbmux client
- **Why:** the protocol is small (3 messages). libimobiledevice brings LGPL, OpenSSL and a build that's awkward on Windows, for features we don't use.
- **Risk:** small details the reference implementation already handles (port byte order, `Listen` on a dedicated socket). We read libusbmuxd's source as documentation.

### D-03 One connection, JSON control + binary video
- **Why:** simplest thing that works. JSON keeps control messages readable in logs. Video stays binary for speed.
- **Revisit if:** control latency behind large keyframes becomes noticeable. The fix is chunking VIDEO payloads, not a second connection.

### D-04 Codec
- **Why H.264 by default:** every Windows GPU has a hardware decoder for it, iOS documents low-latency rate control for it, and at our bitrates the quality is visually transparent.
- **Why HEVC also:** about 30% better compression when a slow link limits 4K60.
- **Not chosen:** ProRes, uncompressed (doesn't fit USB 2), MJPEG (far worse quality per bit, no ISP-level hardware path).

### D-05 FFmpeg D3D11VA
- **Why:** one path for H.264 and HEVC, zero-copy into our D3D11 device, and it **avoids the paid Store HEVC extension** the MF decoder needs.
- **Licence:** LGPL build, dynamic link, a notice in About, our own patches published if we make any.

### D-06 Direct3D 11
- **Why:** it works with FFmpeg D3D11VA, the MF virtual camera's D3D11 sample path, and WinUI's SwapChainPanel. D3D12 or Vulkan would bring complexity with no benefit for a 2D pipeline.

### D-07 Virtual camera technology
- **Why:** MF is the official route on Windows 11, with no kernel driver, Frame Server sharing between apps and full app coverage. Windows 10 doesn't have it, so DirectShow it is. Kernel drivers are excluded by cost.

### D-08 Persistent virtual camera
- **Why:** apps list their cameras when they start. If ours only existed while Cabled was running, users would have to restart Zoom to see it. Persistent with a placeholder is what OBS and others do.
- **Trade-off:** "Cabled Camera" always appears in camera lists.

### D-09 IPC (settled in R2)
- **Decision:** the media source (inside Frame Server, which holds SeCreateGlobalPrivilege) creates `Global\CabledVCam.v1` (a 3-slot frame ring with a header) and `Global\CabledVCam.v1.Frame` (an auto-reset event). The DACL grants interactive users read/write. The engine opens both by name, publishes frames, and reads back the format the app chose. The header carries both directions, so no pipe is needed.
- **Why:** it's the simplest design that works across the session 0 boundary without privileges on the user side. It was measured at 0.5 ms (1080p) and 2.3 ms (4K) from engine to app.
- **Bonus:** the section only exists while an app has the camera open, which tells the engine when to start or stop the phone.

### D-10 / D-11 Split of framing and zoom work
- **Why:** the camera hardware's face detection is effectively free and good, so the phone stays light. Framing policy and tuning live with the UI and are testable without a phone. Zoom done in the ISP is better quality than cropping after encode. Panning is impossible on iOS (zoom is always centred), so panning has to be a crop on Windows.

### D-12 SDR only
- **Why:** no Windows webcam consumer takes HDR, and tone-mapping goes against "no unnecessary processing". Revisit as an optional backlight mode.

### D-14 iPhone app shape
- **Why:** each extension, App Group or capability uses up scarce free-account App IDs and adds signing failure modes under SideStore.

### D-16 C++ engine + C# UI
- **Why:** the virtual camera DLLs must be native, and the pipeline needs C++ for performance. A polished Fluent UI is quicker in C#. The C ABI boundary is narrow: commands, events, a swapchain handle.

### D-17 Inno Setup
- **Why:** simple, free, handles elevation, COM registration and custom steps (registering the virtual camera). MSIX's support for Frame Server COM classes is unclear. WiX is heavier for no gain here.

### D-21 Fake device early
- **Why:** device tests are done by hand, and the phone can only be cabled to one computer at a time. The fake device is what lets most Windows runs finish without you in the loop.

### D-23 Working name
- The display name ("Cabled", "Cabled Camera"), bundle ID, pipe/section names, COM class names and `%APPDATA%` folder are all derived from **one definition per platform** (a CMake/MSBuild property on Windows, an `.xcconfig` on iOS).
- **Exception:** the COM CLSIDs (GUIDs) for the virtual camera are generated once and **never change**, even if the name does. Changing them would leave orphaned cameras on users' machines.

### D-24 MIT licence
- **Allowed:** reading and borrowing from MIT/BSD/Apache sources: the Microsoft Windows-Camera samples, softcam, DirectShow base classes, libusbmuxd *as documentation*. libusbmuxd is LGPL, so we read it but don't copy code.
- **Not allowed:** copying GPL code (OBS, akvirtualcamera).
- FFmpeg ships as LGPL DLLs, with its licence and source location noted in About and the repo.

### D-25 Never code-sign
- **Consequences:** SmartScreen shows "Windows protected your PC" on the installer. UAC shows "Unknown publisher" at the one elevation. Some antivirus products are more suspicious of unsigned binaries.
- **Mitigations:** the README and download page explain the two clicks. Builds are reproducible from public CI, and SHA-256 hashes are published with each release. No packers or obfuscation, which trigger AV heuristics.
- Frame Server loading unsigned DLLs is believed to work, and spike R2 confirms it. If Windows ever *requires* signing for virtual camera sources, this decision has to be revisited.

### D-27 XcodeGen
- **Why:** a hand-edited `project.pbxproj` is unreadable in reviews and merges badly. It also can't be written reliably from a Windows session. `project.yml` is short, readable and regenerates the same project on the Mac and in CI. Cost: `brew install xcodegen` once on the Mac.

### D-28 FetchContent now, vcpkg later
- **Why:** R1 only needs three small MIT/BSD libraries. FetchContent needs no extra tool on CI or the dev PC. FFmpeg (R3) is big and needs prebuilt binaries, and that's where vcpkg earns its place.

### D-26 Rear main by default
- **Why:** much better sensor and lens than the front camera. The preview on the PC replaces the phone screen. Onboarding shows a mount-orientation hint. The last-used lens per phone is remembered after the first session.
